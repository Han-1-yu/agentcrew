# 单进程多 run 并发基线（2026-11-16）

- provider：mock（零费用）+ 每次 LLM 调用注入 200ms 延迟
- 并发槽位上限 `AGENTCREW_MAX_CONCURRENT_RUNS = 8`；每档 2 轮取均值
- 指标口径：`wall` 从发出第一批 POST 到全部 run 进终态；`create_p95` 是 202 响应的延迟（不含排队等槽位）；`CPU 占比` = 进程 CPU 时间 / 墙钟（单进程 Python 上限约 1）

## 判定

- 并发 1：PASS
- 并发 2：PASS
- 并发 4：PASS

## 结论

- 吞吐峰值在 **4 并发**（31.42 run/分，相对单并发 2.17×）；收益低于并发数本身（4×），说明事件循环里有同步段吃掉了部分重叠。8 槽位是**安全护栏，不是吞吐旋钮**。
- CPU 占比 0.27–0.56：进程没把 CPU 打满，大部分时间在等模型；吞吐上不去说明事件循环里有**同步段**（门禁校验 / 文件 IO / ledger 落盘）在串行吃掉并发重叠。
- RSS 52.55 → 56.45 MB（约 +0.98 MB/run），内存不是瓶颈。
- 架构含义：单进程的并发收益随模型延迟变长而变大（同步段占比下降），但同步段与 GIL 决定了它不会线性；要更高吞吐，要么减少同步段（异步化门禁/落盘），要么上多进程/多机（C14 的第二阶段）。

> 口径提醒：mock 下没有真实模型延迟，绝对墙钟不代表生产；这份基线的用处是
> 「同机、同配置下，并发槽位与本地调度是否按预期工作」，以及给后续分布式决策
> 一个可对比的起点。真实模型吞吐要看 `bench.py --real` 与 provider 侧限流。
