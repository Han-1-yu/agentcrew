# ledger 持久化测量（2000 事件/策略）

| 策略 | 吞吐 (events/s) | P50 延迟 (ms) | P95 延迟 (ms) | 最大 (ms) |
| --- | ---: | ---: | ---: | ---: |
| each | 362 | 2.64 | 3.43 | 73.29 |
| batch | 1780 | 0.49 | 0.93 | 4.23 |
| none | 1944 | 0.50 | 0.86 | 3.23 |

> 环境：Windows 本机 / Python 3.12.16 / 策略解析 each（默认）。batch=32；`none` 的崩溃窗口为整个 run（close 收口），`each` 为 0。绝对值随机器浮动，看相对差。

## 读法与结论

- **成本集中在「每条一次 fsync」**：`each` → `batch` 吞吐 362 → 1780 events/s（4.9×），
  再放宽到 `none` 只多 9%（1780 → 1944）——写 JSONL 本身不是瓶颈，磁盘往返才是。
  同口径的 P95 从 3.43ms 降到 0.93 / 0.86ms，单条写不再受 fsync 延迟支配；
  `each` 的 `max` 73.29ms 是一次磁盘抖动，批处理路径把它摊掉了。
- **默认不动**：`each` 是 spec §13.2 的全承诺（Ctrl-C 时最后一条要么完整落盘、要么
  根本不出现），这条语义是审计与 resume 的基础，不为了吞吐牺牲默认行为。
- **哪里该开**：评测（`eval --live`）、批量回放、`worker` 高负载跑批用 `batch`，
  ~5× 吞吐、崩溃窗口只有「最近 N 条（默认 32）」；`none` 只在「整场 run 可重跑、
  断电丢掉也无所谓」的场景用——进程崩溃不丢（OS 页缓存兜底），**断电可能丢掉整个
  run 的事件**。
- **终局不降级**：三种策略在 `close()` 时都强制 fsync 一次；run 终局的持久化承诺
  不因分级打折，窗口只存在于 run 进行中。
- **复跑**：`python scripts/persistence.py --events 2000`（`--target` 可指定写入文件）。
  数字随机器与磁盘浮动，结论看相对差。测量不含进程启动与首条冷写。
