# AgentCrew 能力审查（2026-11-09）

> 审查口径：**在「不同 agent 分别调用不同模型、协同完成一件共同任务」这一目标不变的前提下**，
> 梳理必要功能、比对现状、判断现有结构能否支撑；只有在结构确实无法承载时才建议重构。
>
> 结论先行：**不需要重构。** 现有结构已具备正确的扩展点，本轮三处缺口全部以
> 「新增字段 + 一个分支 + 一个只读端点」的方式补齐，未改动任何既有接口签名。

---

## 1. 审查方法

不采信文档自述，按「读代码 → 跑基线 → 定点验证 → 小步扩展」四步取证：

| 步骤 | 做法 | 结果 |
| --- | --- | --- |
| 读代码 | 逐层核对 18 个子包、131 个模块（36,302 行）的职责边界与依赖方向 | 分层依赖与 `contracts.py` 零依赖契约层一致，无反向依赖 |
| 跑基线 | 全量 pytest（2,899 用例） | 首次全绿；第二次出现 4 个失败，定位为本机解释器段错误（见 §6），与代码无关 |
| 定点验证 | 用 mock 通道读 `run_plan_resolved` / `llm_call` 事件，检查"哪个 agent 用了哪个模型"能否被回答 | **不能完整回答**：事件只有 `role`，没有 `profile` |
| 小步扩展 | 针对缺口做最小改动并补测试 | 3 项缺口闭环，见 §5 |

## 2. 必要功能清单

从目标反推，一个"多 agent、异模型、同任务"的系统必须同时具备八层能力。缺任何一层，
目标都会退化成"换个名字的单 agent"或"无法运营的多 agent"。

| 编号 | 能力 | 为什么是必要的 |
| --- | --- | --- |
| **C1** | 执行体建模 | 要"不同 agent 不同模型"，必须先有一个独立于岗位的执行体对象，承载模型、工具、路径域、预算 |
| **C2** | 角色↔执行体 1:N 绑定 | 岗位是职责，执行体是手段。一个岗位要能挂多个执行体并声明分工 |
| **C3** | 异构模型路由 | 同一 run 内跨 provider（OpenAI 兼容 / Anthropic / 本地），含别名解析、故障转移、冷却 |
| **C4** | 协同机制 | "共同任务"必须落到产物上：分工写、主笔+复核、择优、跨角色咨询、委派 |
| **C5** | 隔离与配额 | 便宜档不能把预算/并发吃光；不同执行体写不同路径，不能互相覆盖 |
| **C6** | 观测与归因 | 必须能回答"哪个 agent 用了哪个模型、花了多少钱、产出被谁复核" |
| **C7** | 配置与治理 | 声明式配置、启动期 fail fast、运行中可切换、快照可审计 |
| **C8** | 评测与回归 | 多执行体路径必须有确定性回归，否则每次调绑定都是盲改 |

## 4. 结论：不重构

### 4.1 结构性证据

现有结构的关键设计恰好是"可扩展"而非"写死"的：

- **角色是数据**：`RoleSpec` 是纯 pydantic 数据，新增角色不改引擎；执行体同理（`AgentProfile`）。
- **解析结果单一事实源**：`RunPlan` 把"声明"与"本次落地"分开，别名、工具收窄、路径域都在启动期算好并落 `run_plan_resolved` 事件。
- **协作对调度器透明**：`TeamAgent` 实现 `execute(task, pack, fix_hints=...)`，内部 fan-out / 聚合，调度器、门禁、checkpoint 零改动。
- **追踪是可插入的**：`TraceContext` 用 contextvar 承载"当前协程在为哪个任务/角色干活"，是天然的归因挂载点。

本轮三个改动全部依赖上述扩展点完成，**没有一处改动既有函数签名、事件形状（只增字段）或状态机**。
唯一的重构是把复核与裁判的模型调用收敛到一个 `_call_as()` 里（消除两处重复的上下文绑定），
属于类内部整理。这就是"结构能支撑"的直接证据——如果结构是错的，这些改动必然要动调度器或状态机。

### 4.2 成本证据

| 维度 | 规模 |
| --- | --- |
| 生产代码 | 131 模块 / 36,302 行 / 18 个子包 |
| 测试 | 144 文件 / 39,201 行 / 2,899 用例 |
| 迭代 | PROJECT-STATE 记录 55+ 轮（R1–R42 + P1–P3 专项） |

重写意味着放弃这 2,899 个用例构成的行为契约，并重新踩一遍已经被记录进
`docs/THREAT_MODEL.md`（46 条威胁、15 条缺口）的安全坑。**收益为负。**

### 4.3 触发重构的条件（供后续判断）

出现下列任一情况才值得重写，目前均不成立：

1. 需要跨进程/跨机分布式调度（当前单进程 asyncio，但 `Checkpoint` + `resume` 锁已为外置化留了口子）；
2. 需要把编排内核替换成事件溯源模型（当前 `TaskBoard` 是内存单一事实源 + JSON checkpoint）；
3. 目标从"交付型流水线"变成"长驻多轮对话体"（当前每次 run 是有限 DAG）。

## 5. 本轮补齐的三处缺口

### 5.1 执行体维度成本归因（C6）

**问题（分两层，第二层是实测才发现的）**

1. `llm_call` 只有 `role`。一个岗位挂了"强推理档 + 便宜档"后，审计流水只能回答
   "backend_dev 花了多少"，回答不了"每一次调用属于哪个执行体"——事后无法按执行体复核账目。
2. 更严重的是**两本账对不上**：进程内的 `agent_budget` 只覆盖 `BaseAgent.execute`
   路径，而 `TeamAgent` 的**复核与裁判是直连模型**。实测一次 5 任务的 run：
   总 LLM 调用 15 次，`run.json` 的 `agent_costs` 只记到 `be_primary` 2 次，
   复核者的 2 次调用凭空消失。运行报告的"执行体"一行因此**系统性低估**
   "主笔 + 复核"模式的真实成本——而这恰恰是多执行体最典型的用法。

**改动**：

| 文件 | 改动 |
| --- | --- |
| `utils/trace.py` | `TraceContext` 增 `profile` 字段 |
| `agents/base_agent.py` | 进入执行即把 `agent_key` 写进追踪上下文；未绑定执行体时落 `default`（与 `RunPlan` 同名），不落 `unknown` |
| `models/factory.py` | `_trace_fields()` 把 `profile` 补进 `llm_call` |
| `runtime/ledger.py` | `event_stats()` 增 `llm.by_profile`；无 `profile` 的历史事件与非执行类调用归入 `unknown`，**不丢弃**，保证分项和 = 总量 |
| `agents/team.py` | 新增 `_call_as()`：复核/裁判直连模型时**同时**绑定 `TraceContext` 与 `agent_budget`，两套上下文 finally 释放。这修掉了上面第 2 条 |

**验证（真实 run，非单测）**：

```
执行体    be_primary 0.00/2次 · be_reviewer 0.00/2次      ← 修复前只有 be_primary
by_profile = {be_primary: 2, be_reviewer: 2, default: 4, unknown: 7}   ← 合计 15 = llm.calls
```

`default` = 未绑定执行体的单 agent 角色；`unknown` = 规划期调用与 G2 门禁评审
（不经过 Agent 执行，本就没有执行体归属）。

**为什么不能只改 ledger**：只把 `profile` 写进事件，`run.json` / 运行报告仍然是错的，
两套账继续分叉。必须让 `agent_budget` 与 `TraceContext` 在同一处绑定，账才平。

### 5.2 复核驱动修订回路（C4）

**问题**：`primary_with_review` 的复核意见只并入 `notes`，主笔不会因此重做。
"复核"沦为装饰——两个模型都跑了，但没有任何一个的产出被另一个改变。

**改动**：`Aggregation.review_rounds`（默认 `0`，上限 3）。

- `0`：逐字保持旧行为（只出意见）；
- `1..3`：复核报出问题（未命中「未发现问题」）→ 意见作为 `fix_hints` 重跑主笔 →
  再复核；最多回灌 N 次，并落 `agent_revise` 事件。

上限 3 是刻意的：再多说明该任务的验收标准本身没写清，应该去改契约而不是加轮数。

### 5.3 执行体计划的读端点（C6/C7）

**问题**：`run_plan_resolved` 已落盘，但只能翻 ledger。缺一个"这次到底哪个 agent 用了哪个模型"的读接口。

**改动**：`GET /runs/{run_id}/agents`

- 取 ledger 中**最后一条** `run_plan_resolved`（resume 多次时以最后一次为准）；
- 历史 run 无该事件时返回 `source: "none"` + 空数组，**不拿配置层面的猜测冒充运行事实**；
- 同步更新 `artifacts/contracts/openapi.yaml`（契约守卫 `test_api_contract.py` 双向锁定）。

与 `GET /runs/{id}/stats` 的 `llm.by_profile` 配对，两个问题都可回答：
**谁用了哪个模型、那个 agent 花了多少钱。**

## 5.4 仍缺的能力（按 ROI 排序，本轮未做）

| 缺口 | 影响 | 建议 |
| --- | --- | --- |
| 执行体级熔断 | provider 挂了会冷却，但"某个 agent 连续失败"不会自停，只会不断消耗返工额度 | 观测先行（`agent_degraded` 已留痕），开关默认关 |
| 成本感知路由 | `models/routing.py` 按健康/用量/权重选池，不读"该 profile 剩余预算"；预算耗尽才降级，属事后 | 在 profile 维度加剩余额度权重 |
| 绑定配置 A/B 评测 | `evals` 能跑固定用例，不能"同一目标、两套绑定、比成本与质量" | 扩 `evals`：配置矩阵 × 用例矩阵 |
| 跨执行体共享工作区 | 同角色多 agent 目前只通过上游产物与 `consult` 交互，没有共享黑板 | 现有 `ContextBus` 可扩，不必新增模块 |
| MCP resources / prompts | 只接了 tools | 按需 |
| 分布式执行 | 单进程，容量未压测 | 触发条件见 §4.3 |
| `web_search` | 需外部搜索 API 与密钥 | 单独设计 |

## 6. 验收证据

```
静态检查   ruff check（7 个改动文件）            All checks passed
定点测试   test_agent_binding.py                30 passed（含 4 项新增）
           test_ledger_api.py                   13 passed（含 3 项新增 + 1 项扩充）
           test_hardening_2026_11.py            13 passed（含 1 项新增）
           test_api_contract.py + test_api_server.py   64 passed（契约双向锁定）
端到端     多执行体 mock run（linear 样例，review_rounds=1）
           任务 5/5 成功 · LLM 15 次 · 执行体 be_primary 2 次 + be_reviewer 2 次
           by_profile 分项合计 = llm.calls（账平）
```

**关于本机随机失败**：全量跑会出现进程级崩溃——堆栈指向 CPython 标准库 `enum.py` 的
`SyntaxError`、退出码 139 `Segmentation fault`、以及 `sitecustomize` 注入期
`SystemError: Negative size passed to PyBytes_FromStringAndSize`。同一文件连跑三次的结果是
「过、过、崩」。项目自身已在 `scripts/test.py` 的文档里记录该现象
（"本机 Windows + 安全软件注入导致随机进程崩溃，崩溃点每次不同、单文件重跑又都能过"）。
此外，pytest 结束时清理 `%TEMP%` 会被本机安全策略拦截（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`），
使 `exit code` 变成 1，但测试本身已跑到 100%。**因此判定以「分批执行 + 崩溃重试 + 定点复跑」为准，
不把环境崩溃计入回归。**

---

## 7. 一句话总结

目标能力**已经具备**，缺的是"多执行体能不能被运营"的三块短板：**复核的花费记漏了、
复核的意见不闭环、解析后的计划不可查**。这三块已在本轮以最小改动补齐
（其中"花费记漏"是端到端跑出来的，不是读代码猜的），结构未被撼动——因此**不重构**。
