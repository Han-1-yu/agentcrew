## 四、已知边界（诚实清单）

1. **容量数字全部来自 mock provider**：真实模型 1–3 秒延迟会改变并发收益的形态；
   `bench.py --real` 是真实侧探测，不是业务压测的替代品。
2. **分布式是「至少一次」语义**：worker 崩溃后租约过期会重跑；`Crew.run` 按同一
   run_id 重跑会覆盖终态记录。任务必须幂等（写同一产物目录）。
3. **共享卷要支持文件锁**：NFS 可用；对象存储不行，要换队列后端（尚未抽象）。
4. **`worker` 拒绝 `gate="both"`**：无人值守进程不会把人工卡点静默降级；需要无人
   值守就显式 `--auto`（等价 `gate=none`）。
5. **队列不做优先级 / 去重 / 延迟重试**；`/runs` 列表只读盘，pending 中的 run
   不出现在列表里（`/status` 可查）。
6. **Windows 本机断言重写偶发崩溃（`0xC0000005`）**：环境问题，全量一律走
   `scripts/test.py`（崩溃隔离跑器），不排期。

## 五、如果继续

1. **队列后端抽象**：把 `RunQueue` 抽成接口，支持 SQS / Redis / 对象存储 + 锁服务；
   这是跨机房部署的前置。
2. **真实 provider 压测**：用 `bench.py --real` 的口径，在 1–3 秒延迟下重跑容量曲线，
   校准 `AGENTCREW_MAX_CONCURRENT_RUNS` 与 worker 数。
3. **优先级与公平**：多租户下 `pending` 的 FIFO 会让大任务挡住小任务；加
   `priority` 与按 key 的配额即可，不需要换队列。
