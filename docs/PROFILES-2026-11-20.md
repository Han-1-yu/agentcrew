# 执行体档案：使用场景、差距与完善方案（R69，2026-11-20）

> 范围：`AgentProfile` 配置模型、`agents` CLI、Studio「执行体档案」页，以及它们与
> 角色绑定 / RunPlan / 台账的连接方式。
> 方法：先读代码与现有文档还原真实使用方式，再对照成熟产品的 agent 管理实现，
> 最后按「不改主配置、写入有保护、问题可定位」三条约束落地。
> 调研时间：2026-11-20；外部文档以当时可访问版本为准。

---

## 1. 结论摘要

执行体档案本身的能力并不弱：模型覆盖、备用链、工具收窄、写入范围、成本 /
RPM / 并发上限、温度与输出长度都有，运行期也真的按这些字段解析和记账。
**问题集中在「管理面」**——它只有一块只读展板：

- 默认安装下页面是 **0 档案 + 两段空态文案**，没有任何创建入口；
- 想改档案只能去手写 `agentcrew.yaml`，页面只能「导出 YAML 片段」再让人自己粘；
- 看不到档案来自哪里、是否覆盖了同名定义、绑定后是否还能启动；
- 看不到「这份档案到底有没有被用过、花了多少钱」；
- 删除、备份、导入、复制、生效预览都不存在。

本轮把它补成可用的档案工作台：**一档案一文件（`agents.d/<key>.yaml`）+ 保存前
绑定校验 + 诊断分级 + 跨 run 用量 + 卡片/编辑器/导入导出**。同时守住两条边界：
不重写 `agentcrew.yaml`（注释与顺序不动），任何写操作都可回退（`.bak` + `.trash`）。

## 2. 现状：这个功能到底用来干什么

### 2.1 三层结构

| 层 | 载体 | 回答的问题 |
| --- | --- | --- |
| 角色（RoleSpec） | 8 个内置 + `roles.d/*.yaml` | 这个岗位**该做什么**（职责/边界/产出契约） |
| 执行体档案（AgentProfile） | `agents.profiles` / `agents.d/*.yaml` | 这活**怎么干、用谁干、花多少**（模型/工具/路径/预算） |
| 绑定（RoleAgents） | `roles.<role>.agents` | 一个角色**可以同时挂几个执行体**，各是什么职责 |

解析顺序（`agents/plan.py`）：`profile.model` → `RoleSpec.model` →
`role_bindings` → `default_model`；工具取「角色授权 ∩ 档案白名单」（只能收窄）；
多执行体再按 `primary_with_review / split_by_path / best_of / merge` 汇总。

### 2.2 真实使用场景

从代码、测试和 `docs/role-agent-binding-design.md` 可以还原出七类用法：

1. **成本分层**：同一角色「便宜档主笔 + 强推理档复核」，用 `cost_ceiling_usd`
   管单任务、`run_cost_ceiling_usd` 管整场。台账里 `llm_call.profile` 就是为
   了回答「哪个档在花钱」而加的（`utils/trace.py` 的注释写得很明确）。
2. **强弱模型分工**：`primary_with_review`，复核意见可回灌主笔修订
   （`review_rounds` 1–3 轮）。
3. **最小权限**：复核者只给 `read_file/list_files/grep`，从工具层面杜绝「顺手改稿」。
4. **按目录分工**：`split_by_path` + 互斥 `path_scope`，两个执行体并行写不同目录，
   产物落盘前由 `ArtifactStore` 拒绝越界。
5. **N 选 1 / 合并**：`best_of` 指定 judge（裁判不能参赛），或 `merge` 汇总。
6. **实验对比**：同一角色换不同执行体，用 `agents --json` / 台账对比成本与结果；
   评测变体（`load_yaml_config`）也复用同一套 `agents.profiles` 形状。
7. **模板复用**：把一份调好的档案导出 YAML，贴到另一个项目/团队。

### 2.3 现状能力矩阵（改造前）

| 能力 | CLI | Studio | 说明 |
| --- | --- | --- | --- |
| 查看档案 | `agents` / `agents --json` | ✅ 卡片 | 字段较全 |
| 查看绑定 | ✅ 文本 / JSON | ✅ 矩阵 | 只显示已绑定角色 |
| 导出片段 | ✅ `--yaml` | ✅ 复制全部 | 只能整段导出 |
| 新建 / 编辑 | ❌ | ❌ | 只能手写 YAML |
| 删除 / 备份 | ❌ | ❌ | 无 |
| 导入 | ❌ | ❌ | 只能手粘 |
| 配置诊断 | ❌ | ❌ | 启动时才报错 |
| 生效预览 | ❌ | ❌ | 看不到工具交集 |
| 来源 / 覆盖关系 | ❌ | ❌ | 同名定义谁生效未知 |
| 使用量 / 成本 | ❌ | ❌ | 台账有数据，页面不展示 |

## 3. 不足：按用户旅程拆

### 3.1 发现：页面不告诉人「这东西能干什么」

空态只有两句「在 agentcrew.yaml 的 agents.profiles 段定义执行体后……」。
对一个刚装好的用户，这是一条**死路**：没有示例、没有模板、没有创建按钮，
也不知道该先建档案还是先绑定。

### 3.2 创建：唯一的入口是手写 YAML，且没有护栏

`AgentProfile` 是 `extra="forbid"`，字段名拼错（`tittle` / `cost_ceiling`）会直接
让 **整个配置读不出来**——一个执行体写坏，所有 run 起不来。手写时还没有任何
「工具是否超出角色授权」「模型别名是否合法」的即时反馈。

### 3.3 校验：错误要等到下一次启动才暴露

`validate_bindings` 在启动期 fail-fast 是对的，但用户改档案时看不到：
工具扩权、`split_by_path` 路径重叠、`best_of` 裁判参赛、`primary_with_review`
没有复核者……这些都应该在**保存前**说清楚。

### 3.4 绑定：矩阵只回答「谁绑了谁」

- 没有「未绑定角色」清单，8 个角色里哪些还在走单执行体看不出来；
- 断链（ref 指向不存在的档案）在页面上与正常绑定长得一样；
- 档案卡片不显示「被哪些角色用」，反过来也看不到影响面。

### 3.5 运行：没有「生效预览」

档案的 `tools` 是「与角色授权的交集」，`model` 是四级继承。用户看到的卡片写
「工具：继承角色」时，无法知道**这个角色下**最终能拿到哪几个工具。多执行体
场景下这是最容易配错的地方。

### 3.6 复盘：台账里有金矿，页面不挖

`llm_call` 事件从 R44 起带 `profile`，`event_stats` 也已经按 profile 分桶；
但档案页没有调用量、成本、最近使用时间。于是「这个档案还有人用吗」「便宜的档
真的更便宜吗」只能自己去翻 `output/*/ledger.jsonl`。

### 3.7 维护：没有来源、没有版本、没有回收站

- 同名档案可能同时存在于 `agentcrew.yaml` 和外部文件，谁生效没有标识；
- 改错了没有 `.bak`，删错了没有回收站；
- 导入只能整段复制，不能先校验、不能选择覆盖。

### 3.8 结构性问题：写配置的成本高于收益

原设计文档（`docs/WorkBuddy功能对齐-差距与实施.md` §4.1）明确写过不做程序化
写配置，理由是「写坏 config 风险高于收益，且需要重启才能被读到」。这个判断
在当时是对的——因为唯一可写的位置是主配置。**一档案一文件**之后，两个前提都
不成立了：单文件写坏只影响一份档案，CLI 每次调用都是新进程，天然读到新配置。

## 4. 成熟项目怎么做

| 产品 | 关键做法 | 对本项目的启发 |
| --- | --- | --- |
| **Claude Code Subagents** | `/agents` 交互管理：查看（内置/用户/项目/插件）、引导式创建、编辑工具权限、删除；`claude agents` 按来源分组并标出「被更高优先级覆盖」；文件是 `.claude/agents/*.md`，YAML frontmatter 含 `name/description/tools/model`，同名按 项目 > 用户 > 插件 覆盖 | 一档案一文件；来源与覆盖必须可见；创建/编辑/删除是管理页的基本盘 |
| **VS Code Custom Agents** | 工作区 / 用户两级 `.agent.md`；编辑器创建、编辑、删除；「诊断视图」列出所有已加载 agent 与错误；工具列表有明确优先级；可设 `user-invocable` 控制是否出现在选择器 | 诊断要成为一等公民；「可见/可调用」与「定义」分离；工具白名单要能看懂 |
| **Copilot Studio（agent flow）** | 保存即记版本，可对比/恢复；Flow checker 把错误/警告一次列全，有错不能发布；发布前用 Test 面板跑真实输入；Analytics 看运行数、失败率、时长 | 保存前校验 + 问题分级；用量/效果面板；版本与回滚（本轮先做 `.bak`/`.trash`） |
| **Dify New Agent** | 每个 agent 是独立资源，「一处维护、多处复用」；Duplicate 复制变体；DSL 导入/导出（YAML，导入先做版本兼容检查）；Build Draft + Preview + 发布；强调「谁维护、在哪被用、出错怎么查」 | 复制为新档案；导入先校验；卡片回答「谁在用」；预览生效结果 |
| **CrewAI** | `config/agents.yaml` 声明式定义（role/goal/backstory/llm/tools/max_rpm/max_iter…）；Visual Agent Builder 提供表单、实时测试与模板库 | 表单化编辑 + 模板；`max_rpm` 等运行参数属于档案而不是代码 |
| **OpenAI AgentKit / Agent Builder** | 可视化编排 + Preview 运行 + 完整版本管理；Publish 生成命名版本，可回滚；模板起步 | 「先预览再保存」的心智；模板降低首次创建门槛 |
| **LiteLLM / 网关侧预算**（横向对照） | 预算与限流挂在 key/team 上，按调用记账，超额拒绝 | 档案级预算应与台账同源，能按档案复盘（本项目已有 `by_profile`） |

### 4.1 提炼出的七条模式

1. **文件即定义，文件名即标识**（Claude Code / VS Code / CrewAI）：可 diff、可 review、可版本控制。
2. **多来源 + 明确优先级 + 覆盖可见**（Claude Code / VS Code）：不是「只允许一个地方」，而是「说清楚谁赢」。
3. **管理面必须能增删改**（全部）：只读文档页不叫管理。
4. **保存前校验，错误/警告分级**（Copilot Studio / VS Code Diagnostics）：错误阻止，警告解释后果。
5. **生效预览 / Preview**（Agent Builder / Dify / Copilot Studio）：让用户在保存前看到「真正会用什么」。
6. **复制与导入导出**（Dify / Agent Builder）：Duplicate 是最低成本的迭代方式；导入必须先校验。
7. **用量与效果可见**（Copilot Studio Analytics / Dify 观测）：回答「还在用吗、花了多少、最近一次什么时候」。

### 4.2 刻意没照搬的

- **完整版本历史 / 发布态**：需要一套存储与迁移，收益在本项目当前阶段低于成本；先用 `.bak` + `.trash` 保证可回退。
- **在线试跑（Test 面板）**：一次真实 run 成本高、副作用大；本轮用「生效预览」替代，试跑留给 run 页面。
- **组织级共享 / 市场**：没有多租户后端，强做会变成伪需求。

## 5. 完善方案

### 5.1 设计原则

1. **不重写主配置**：`agentcrew.yaml` 的注释、顺序、手工排版一律不动。
2. **一档案一文件**：`agents.d/<key>.yaml`，文件名即 key；可单独 review / 回滚。
3. **写操作有保护**：原子写（同目录临时文件 + `os.replace`）、覆盖前 `.bak`、删除进 `.trash`、key 路径穿越校验。
4. **保存前跑执行期同一套规则**：工具收窄、`split_by_path` 互斥、`best_of` 裁判、模型别名解析；不复制规则。
5. **诊断分级**：error 阻止启动/保存，warning 解释后果，info 提示但不打扰。
6. **UI 只做呈现与编排**：前端不生成 YAML、不直接写文件；所有写操作走 `agents --save|--delete`。

### 5.2 存储与加载

```
agentcrew.yaml            # 手工配置（保持原样）
agents.d/
  fast-writer.yaml        # 一份档案一个文件
  strict-reviewer.yaml
  .trash/                 # 删除的档案（可恢复）
  fast-writer.yaml.bak    # 最近一次覆盖前的备份
```

- 加载优先级：`agents.d` **覆盖** `agentcrew.yaml` 的同名定义（与 Claude Code 的
  项目 > 用户一致）。被覆盖的事实会在卡片和诊断里明确标出，绝不静默。
- `profiles_dir` 可配置；未配置时取配置文件同级的 `agents.d/`，目录不存在则完全
  不改变既有行为。
- 坏文件不阻断整个配置：可加载的照常生效，问题进 `profile_errors`，由诊断页
  与 `agents --check` 展示；**绑定到坏档案的角色仍在启动期被拒绝**，并明确
  指出是哪份文件。

### 5.3 CLI

```bash
python main.py agents                      # 列表 + 绑定
python main.py agents --json               # 档案 + 来源 + 绑定 + 诊断 + 目录
python main.py agents --check [--json]     # 错误/警告/提示逐条
python main.py agents --usage [--json]     # 跨 run 的调用/成本/最近使用
python main.py agents --save - --json      # 从 stdin 保存（支持批量）
python main.py agents --save x.yaml --force --dry-run
python main.py agents --delete fast-writer [--force]
python main.py agents --yaml --key fast-writer
```

### 5.4 Studio 信息架构

1. **页头**：标题 + 一句话定位 + 刷新 / 导入 / 新建。
2. **状态条**：档案 / 已绑定 / 未绑定 / 有问题（可点筛选）+ 档案目录（可打开）。
3. **诊断面板**：错误默认展开，警告/提示可折叠；每条带定位按钮。
4. **工具栏**：搜索（key/名称/能力/绑定角色）+ 六个筛选（全部/已绑定/未绑定/有问题/agents.d/YAML）。
5. **档案卡片**：名称 + key + 来源徽标、能力描述与标签、模型/工具/写入/预算、
   跨 run 用量、绑定角色（职责/权重）、编辑/复制/导出 YAML/删除。
6. **编辑器（宽模态）**：模板 → 基本信息 → 模型 → 工具与边界 → 预算与限流 →
   按角色生效预览 → 行内错误；新建/编辑/复制共用。
7. **导入**：粘贴或文件载入，先校验再导入，可选覆盖。
8. **绑定矩阵**：已绑定角色逐行展示断链；未绑定角色折叠；点击档案 chip 直接编辑。

### 5.5 关键取舍

| 问题 | 取舍 | 理由 |
| --- | --- | --- |
| 写 YAML 还是写独立文件 | 独立文件 | 主配置注释/顺序不丢；单文件损坏影响面小 |
| 目录优先还是 YAML 优先 | 目录优先 | UI 编辑立即生效；同名覆盖显式提示 |
| 坏文件 fail-fast 还是降级 | 降级 + 诊断 | 否则用户无法用 UI 修复；绑定时仍 fail-fast |
| 删除物理删还是回收站 | 回收站 | 编排配置误删的代价远高于留一份副本 |
| 是否做版本历史 | 暂不做 | `.bak` 已覆盖「改错了」；完整版本需要独立设计 |
| 是否做在线试跑 | 暂不做 | 成本/副作用高；先用生效预览消除歧义 |

## 8. 后续（未排期）

1. **版本历史**：每次保存留一份带时间戳的版本，支持 diff/恢复（可复用 `.bak` 思路）。
2. **在线试跑**：选一个任务契约 + mock/live，跑单执行体验证工具与输出（成本可控时再做）。
3. **绑定编辑进档案页**：目前仍跳设置页；可把「勾选职责 + 汇总模式」搬过来，复用现有校验。
4. **用量趋势**：按天聚合调用/成本，回答「这个档最近是不是变贵了」。
5. **档案市场/团队共享**：需要多租户与权限模型，当前不做。
