先界定检索服务的产品边界：谁在用、检索什么、返回什么顺序，再把每条要求落成可判定的验收标准。

```markdown file=docs/PRD.md
# 内部知识库检索 · 产品需求

## 1. 背景

团队的决策散在周报、故障复盘、设计文档里。想知道「当时为什么不用消息队列」，
只能靠记忆去翻某个人某个月的文档。检索服务要解决的就是这件事：给一个关键词，
按相关度返回文档片段，并说明为什么命中。

## 2. 目标用户

| 用户 | 场景 | 诉求 |
|---|---|---|
| 新入职同学 | 不了解历史决策 | 用自然语言关键词找到原始上下文 |
| 值班工程师 | 上次同类故障怎么处理的 | 按错误码检索到复盘文档 |
| 架构评审人 | 判断方案是否与既有约定冲突 | 检索到被否决的备选方案与理由 |

## 3. 检索语义

- 输入是关键词串，按空白切分；多个关键词之间是**与**语义，只返回全部命中的文档。
- 英文按小写归一，中文按双字切分（不引入分词模型，避免索引与查询两侧行为不一致）。
- 每个结果返回：文档 id、命中关键词数、标题与摘要片段。

## 4. 排序

排序按两级：

1. **命中词数**降序 —— 命中三个词的文档一定比只命中一个的更相关；
2. 命中词数相同时按**文档 id** 升序 —— 保证同一查询两次返回顺序完全一致。

不引入 TF-IDF 之类的权重：语料规模在万级以内，权重带来的收益抵不过
「同一查询结果会随语料变化而抖动」的代价，排序不可复现会让复盘时的
「我上次明明搜到过」变成无解争论。

## 5. 验收标准

- AC-01 单关键词查询返回全部包含该词的文档。
- AC-02 多关键词查询只返回同时包含全部关键词的文档。
- AC-03 结果按命中词数降序、同分按文档 id 升序。
- AC-04 空查询返回空列表而不是全部文档。
- AC-05 删除文档后再次查询，结果中不再出现该文档。
```

PRD 已按契约路径产出，检索语义与排序规则可直接作为设计与验收依据。
