按 PRD 的检索语义做分层设计：索引层只管倒排表，服务层只管协议，两条实现路径互不依赖，由用例层汇合验证。

````markdown file=docs/design.md
# 知识库检索 · 架构设计

## 1. 模块划分

```
kb/api.py     服务层：create_app、查询路由、结果序列化
    ↓
kb/index.py   索引层：InvertedIndex、分词、求交、打分排序
```

两条实现路径**并行开发、互不依赖**：

- 路径 A（`kb/index.py`）：纯数据结构，输入文档、输出结果 id 列表，不知道 HTTP 存在；
- 路径 B（`kb/api.py`）：只管路由与序列化，把检索委托给索引层，自己不实现任何打分。

汇合点在用例层（`tests/test_index.py`）：它同时 import 两侧，
因此两条路径可以各自先跑通单测，再在用例里验证「路由返回的顺序 == 索引层给的顺序」。

依赖方向单向：`api` 依赖 `index`，`index` 不 import `api`。这条约束让索引层
可以在没有 Web 框架的环境里被单测，也是它能被将来别的入口复用的前提。

## 2. 倒排索引

**结构**：`dict[str, set[str]]` —— 词到文档 id 集合的映射。文档正文另存
`dict[str, str]`，只在需要摘要时读取，避免检索路径上反复拿全文。

**构建**：`add(doc_id, text)` 分词后把 doc_id 塞进每个词的集合；重复添加同一
doc_id 时先清理旧词条，保证「重新索引一篇文档」不会在旧词上留下幽灵命中。

**内存布局**：集合而非列表 —— 求交是核心操作，集合的交集是 O(min(m,n))，
且天然去重；代价是丢掉词频，这与 PRD §4「不引入 TF-IDF」的取舍一致。

## 3. 查询语法

只支持一种语法：空白分隔的关键词，语义为**与**。

- `foo bar` → 同时含 foo 与 bar；
- 不支��� `OR`、通配符与短语：这类语法一旦引入，查询与索引两侧的分词规则
  必须严格同步，否则会出现「索引里有、搜不到」的静默错误；
- 空查询返回空列表 —— 把空查询当成「全部文档」会让调用方误以为检索到了东西。

## 4. 失败与一致性

检索不抛异常：未知词返回空集合，求交后为空即返回空列表。索引层是纯内存结构，
进程重启即重建，因此不涉及部分失败的中间态；文档删除是同步的，返回后立即可见，
不存在「删了但还能搜到」的窗口。
````

设计文档已按契约路径产出，模块划分与倒排结构可直接作为实现依据。
