按 PRD 的统计口径做了设计：模块按「读 → 解析 → 聚合 → 渲染」单向依赖切开，聚合算法用最近秩分位，异常行统一走 skipped 计数而非抛错。

````markdown file=docs/design.md
# logstat 设计

## 1. 模块划分

依赖方向单一，箭头只能向下：

```
cli.py      命令行解析与输出选择
   ↓
core.py     analyze：编排 解析 → 聚合 → 统计量
   ↓
parser.py   单行日志 → Record，解析不了返回 None
aggregate.py 窗口聚合、状态码计数、分位计算
   ↓
model.py    Record / Stats 两个不可变数据结构
```

- `parser` 不认识统计，只负责把一行文本变成一个 `Record` 或 `None`；
- `aggregate` 不做 IO，输入是 `Record` 列表，输出是 `Stats`；
- `core.analyze` 是唯一的编排点，命令行与将来可能的 HTTP 入口都调它；
- `cli` 只做参数与渲染，不参与计算，因此可以整体替换而不影响口径。

反向依赖被排除：任何模块都不 import `cli`，所以统计逻辑可以单测而不启动进程。

## 2. 聚合算法

**时间窗口**：把时间戳截断到窗口上界（默认 1 分钟），用截断后的值做 key。
这样同一分钟内的请求落在同一个桶里，跨窗口的请求不会因为边界对齐方式不同而漂移。
每个桶记 `count` 与 `errors`（状态码 ≥ 500 记一次）。

**分位**：用最近秩（nearest-rank）而不是线性插值。日志耗时的分布是长尾，
插值出来的分位数对应不到任何一条真实请求，值班时无法回查「是哪一条慢」；
最近秩取的永远是集合里真实存在的一个值，可以反查。

**状态码分布**：`Counter` 计数后按状态码升序输出，保证同一份日志两次运行输出逐字节一致，
便于把输出直接 diff。

## 3. 异常行的处理策略

解析失败不抛异常，原因有三：

1. 日志是流式追加的，最后一行经常是写了一半的，抛错会导致整次统计失败；
2. 启动横幅、健康检查的裸文本会混进同一个文件；
3. 值班场景下「少算一行」远好过「一条命令直接报错退出」。

因此 `parser.parse_line` 对任何不满足字段数或数值格式的行返回 `None`，
`core.analyze` 把 `None` 计入 `skipped` 并继续。`skipped > 0` 时 cli 在表格下方
追加一行提示，避免用户以为日志是干净的。
````

设计文档已按契约路径产出，模块划分与聚合算法可直接作为实现依据。
