# AgentCrew 能力完善路线 —— 以能力为主轴，对准市面主流 Agent

> 日期：2026-11-12。依据：`PROJECT-STATE.md`（R50 后状态）+ 本地源码定点核验 + 2026-11 市面公开调研。
> 本文是《AgentCrew开源对标调研与完善方案.md》（2026-11-08）的**后继**：该方案的 P0/P1/P2 已基本由 R35–R50 落地。
> **组织方式：能力优先。** 不按阶段推进叙事，而是把"一个合格的市面 agent 应该具备的能力"逐项列出，
> 每项讲清：市面基线 → 我们的现状（带证据）→ 目标状态 → 落地做法 → 验收标准 → 依赖与边界。
> 实施顺序只在 §5 作为依赖关系的推导结果给出，不是本文的主轴。

---

## 0. 总判断

**项目的短板不在"稳不稳"，而在"能不能干活"和"别人能不能用上"。**

编排治理（DAG/条件分支/委派/多级主管/HITL/断点调试）、模型韧性（7 provider/故障转移/预算/限流）、
安全审计（RBAC/威胁模型/契约守卫/3115 用例）已达到甚至超过多数开源同类框架——**这些不是差距，不要重复投入**。

用"能力五支柱"看 2026 年市面主流 agent（Manus、Devin、OpenHands、浏览器 agent、Coding CLI），
AgentCrew 的画像非常清晰：

| 支柱 | 市面主流 | AgentCrew |
| --- | --- | --- |
| ① 获取信息（搜索/浏览/读文档） | 标配，浏览器操作成独立赛道 | **窄**：只有单页只读抓取 |
| ② 操作环境（安全执行代码/命令） | Docker/microVM 沙箱，默认敢跑 | **缺**：无系统级沙箱，默认关 |
| ③ 验证产出（跑起来看结果） | 执行→观察→修正闭环 | **缺**：生成的代码从不被系统执行 |
| ④ 理解多模态（看图/文档） | 截图理解普及 | **缺**：纯文本通道 |
| ⑤ 融入生态（被调用/触发/协作） | MCP 双向 + A2A + 事件驱动 | **半**：MCP 只有客户端，无触发器 |

而支撑这五根支柱的"治理底座"（调度/门禁/恢复/审计/评测框架），AgentCrew 反而是市面少见的强。
**完善方向 = 保住治理底座，逐根补齐支柱。** 下文按支柱展开 14 项能力（C1–C14）。

## 2. 能力详解（本文主体）

每项统一六段：市面基线 / 现状证据 / 目标状态 / 落地做法 / 验收标准 / 依赖与边界。
工作量为人日估算（含测试与文档，按本仓"回归钉住"口径），供排期参考。

### C1 · 联网搜索（web_search）｜支柱①｜P0｜≈1 人日

- **市面基线**：通用 agent（Manus 等）以深度调研为一等场景；没有搜索，"调研/分析/写报告"类目标全部做不了。
- **现状证据**：`tools/network.py` 开头明言"只做只读抓取，web_search 依赖外部搜索 API 与密钥……"；
  §7 已估 1 人日，一直未做。当前只有 `web_fetch`（单页、仅公网 80/443、拒私网/重定向）。
- **目标状态**：Agent 能在任务中主动检索互联网、拿到多条结果并择优读取，调研类目标可端到端完成。
- **落地做法**：可插拔 `SearchProvider` 接口（密钥走 env，与 provider 目录同口径）+ 结果截断/去重 +
  mock 夹具离线回放；默认关闭。SSRF 与文本上限沿用 web_fetch 标准。
- **验收标准**：mock 端到端进 linear 样例；真实通道 smoke 一次；四通道登记齐全。
- **依赖与边界**：无前置依赖，可立即做。需外部搜索 API 密钥——这是它被搁置的原因，
  但"密钥走 env、默认关、离线可测"的既有先例（R3 provider）已能化解，不构成不做的理由。

### C2 · 安全代码执行（沙箱后端）｜支柱②｜P0｜≈3–5 人日

- **市面基线**：OpenHands 全部操作在 Docker 容器内执行；Codex CLI 沙箱默认开、Claude Code 提供
  sandboxed bash；商用侧 E2B（Firecracker microVM，冷启动约 150ms）成主流框架通用执行后端。
  **"能跑代码"和"敢跑代码"是两件事，市面产品两者都做了。**
- **现状证据**：`run_python` 仅 `-I` 隔离 + 超时 + 路径检查，无网络/资源/系统调用隔离
  （威胁模型 G-9），R35 起默认关闭。这是"不敢让 agent 跑代码"的根因。
- **目标状态**：生产环境可放心让 agent 执行代码——出网、读宿主文件、资源耗尽都被隔离拦住。
- **落地做法**：抽 `ExecutionBackend` 接口——`local`（默认，现行为逐字不变）与 `docker`（可选）两实现；
  run_python 与后续 run_tests/浏览器工具共用。docker 模式：非 root、网络默认禁、CPU/内存上限、
  只挂工作区卷；复用 R50 已交付的 Docker 三件套经验。无 Docker 环境时 fail loud，不静默降级。
- **验收标准**：逃逸用例（出网/读宿主/资源耗尽）在 docker 模式被拦；local 模式既有用例一行不改通过。
- **依赖与边界**：无前置依赖。不引 K8s/gVisor/云沙箱（延续既有方案 §5.4）；microVM 留接口不实现。
  与"零依赖红线"的关系：沙箱是**可选后端**、默认 local 行为不变，同 R35"run_python 默认关"先例，
  不破坏离线可测；文档须写清"生产跑代码请开 docker 后端"。

### C3 · 执行-测试-修正闭环（run_tests + 执行校验）｜支柱③｜P0｜≈2–3 人日

- **市面基线**：Devin/OpenHands 的核心循环是"写代码→跑测试/跑服务→看报错→改"，
  产出质量靠**真实执行**兜底，而不是靠评审模型打分。
- **现状证据**：§7 功能边界明写"不执行生成的代码（G1 只静态校验）"；R37 里那份 pytest 18 例全过
  是**人工**跑的，系统本身从不执行产物。G2 评审模型"看代码打分"，与市面"跑起来看结果"有本质差。
- **目标状态**：产物在交付前被真实执行验证，失败自动进入既有自修正通道，形成可信闭环。
- **落地做法**：新增 `run_tests` 内置工具（沙箱内跑 pytest，输出截断回灌）；G1 增加可选"执行校验"档
  （默认关），失败输出走既有 `max_self_corrections` 自修正通道，**不新增第二条返工路径**。
- **验收标准**：真实模型端到端"生成函数+测试→首跑失败→自修正→通过"，ledger 可见完整闭环；
  开/关执行校验的产物质量对照进 eval 矩阵。
- **依赖与边界**：**依赖 C2**（在沙箱里跑才安全）。这是与 Devin/OpenHands 的最大能力差，
  也是"治理强"能否转化为"产出可信"的关键一步。

### C4 · 多模态输入（图像理解）｜支柱④｜P1｜≈3–5 人日

- **市面基线**：主流模型普遍支持图像，agent 用"截图理解→改前端→再截图对比"完成 UI 任务；
  纯文本 agent 在 UI/文档/图表类任务上明显吃亏。
- **现状证据**：providers 无图像内容 parts 通道（全仓检索无 vision 路径，仅 `model_copy` 误匹配）。
  frontend_dev 角色目前是"盲写"前端。
- **目标状态**：目标可附图片，agent 能看图理解需求/核对 UI，解锁截图类工作流。
- **落地做法**：`Message` 增加内容 parts（image_url/base64），OpenAICompat/Anthropic 透传，
  能力位 `supports_vision` 默认 False（与 supports_tool_calls 同先例）；图片进产物区、Studio 可预览；
  纯文本路径逐字节不变。
- **验收标准**：真实模型"截图→复刻/修改前端"端到端；无 vision 能力的 provider 明确降级提示。
- **依赖与边界**：无硬前置。与 C6 浏览器联动后价值最大（截图→改→再截图）。

### C5 · 文档 RAG（领域知识）｜支柱①④｜P1｜≈3–5 人日

- **市面基线**：知识库/文档问答是企业 agent 落地的常见诉求，RAG 管线是标配。
- **现状证据**：向量通道已有（R27 经验库 / R29 实体记忆，含磁盘缓存 + HashEmbedder 本地退化），
  但**只服务团队自身的经验/实体库，没有外部文档摄取管线**。经验库是"团队记忆"，不是"领域知识"。
- **目标状态**：用户可挂载文档集（md/txt/代码目录），agent 规划与执行时检索注入相关领域知识。
- **落地做法**：复用 R27 embedder + 磁盘缓存，新增摄取管线（分块→JSONL 向量库），检索注入 PM 与执行上下文；
  千级文档用现有 JSONL+余弦即可，**不引向量数据库服务**，万级再评估（延续"不引重型依赖"红线）。
- **验收标准**：真实文档集上检索命中率对照纯 BM25 有可测提升（进 eval 矩阵）；离线 HashEmbedder 退化可跑。
- **依赖与边界**：复用既有向量通道，无新重型依赖。

### C6 · 浏览器操作｜支柱①②｜P1｜≈5–8 人日（先借后建）

- **市面基线**：浏览器操作是 2026 年主战场之一（Browser Use、各家 AI 浏览器），
  "替你操作网页"是通用 agent 的常态能力。
- **现状证据**：全仓无 playwright/selenium/browser-use 代码（已检索核验，仅提示词/注释提及"浏览器"）。
- **目标状态**：agent 能打开网页、提取信息、填表提交，完成需要真实浏览器交互的任务。
- **落地做法**：**先借后建**——第一步零开发：接现成浏览器 MCP server（R13 客户端已支持），
  写配置模板 + `tool_permissions` 精确授权 + 边界文档；第二步视需求内置 playwright 工具
  （可选依赖组 `pip install agentcrew[browser]`，默认不装，跑在 C2 沙箱里）。
- **验收标准**：真实网页"提取信息/填表"端到端各一次；与 `untrusted_inputs` 只读预设联动，
  注入边界写进 THREAT_MODEL。
- **依赖与边界**：内置版**依赖 C2**（沙箱）；借 MCP 版无前置。不自研浏览器内核。
  扩大注入面，guardrails 规则须同步扩展。

### C7 · 暴露为 MCP server｜支柱⑤｜P1｜≈2–3 人日

- **市面基线**：MCP 已是工具接入事实标准，主流框架双向（既是客户端也是服务端）。
- **现状证据**：只有客户端；R13 明确把"把 agentcrew 自身暴露成 MCP server"列为未做。
- **目标状态**：任何 MCP 客户端（Claude Desktop/Cursor 类）都能把 AgentCrew 当一个工具/同事来调用。
- **落地做法**：把 create_run / status / approvals / approve 暴露为 MCP tools，复用现有 API 层 + RBAC + 审计；
  stdio 与 streamable HTTP 双传输（协议实现已在 mcp/ 包，反向复用）。
- **验收标准**：官方 MCP 客户端互通实跑；越权调用被 RBAC 拒绝并留痕。
- **依赖与边界**：无前置。**成本最低、杠杆最大**——让所有 MCP 生态瞬间成为入口，
  "多 agent 协作"不再限于进程内 8 个角色。

### C8 · 事件触发 / 定时运行｜支柱⑤｜P1｜≈2–3 人日

- **市面基线**：Manus 2.0 Studio 支持事件触发自动化；"人不在场也能跑、外部事件能触发"是通用 agent 常态。
- **现状证据**：只有出站 Webhook（R12/R14/R15）；入站触发与调度均无。
- **目标状态**：run 可由定时计划或外部事件无人值守地发起。
- **落地做法**：定时运行（cron 表达式，进程内调度即可）+ 入站 Webhook 触发 run（HMAC 校验，
  复用 R12 签名语义）；RBAC 新增触发作用域；触发来源进 ledger。
- **验收标准**：定时与事件触发各端到端一次；伪造签名被拒。
- **依赖与边界**：无前置。从"人盯着跑"变"无人值守跑"。

### C9 · A2A 互操作｜支柱⑤｜P2｜按需

- **市面基线**：A2A 由 Linux Foundation 托管，2026-04 官方宣布 150+ 组织支持、v1.0 稳定版与签名 Agent Card；
  微软官方多智能体架构文档推荐"MCP 接工具、A2A 跨平台接 agent"。
- **现状证据**：未做。
- **目标状态**：AgentCrew 能被其他平台的 agent 发现并委派任务。
- **落地做法**：最小形态——Agent Card + 最小任务端点（LF v1.0）。
- **验收标准**：与一个真实 A2A 客户端完成发现→委派→回执。
- **依赖与边界**：**采纳度有争议**（有观点认为用例与实现负担限制普及），不提前重投；
  出现真实跨平台集成需求再立项。

### C10 · 对话式入口 + run 中途引导｜支柱⑤｜P2｜产品决策

- **市面基线**：对话即入口，用户可在 run 进行中补充信息、调整方向。
- **现状证据**：Studio 对话页是 ledger 只读聚合展示（R43），干预只有审批单/断点。
- **目标状态**：对话可作目标入口与进度查询，run 中途可引导。
- **落地做法**：对话只作目标入口与进度查询，**不改确定性调度内核**；中途引导走既有审批/委派通道。
- **验收标准**：对话发起 run、中途经审批通道注入一条引导并被执行。
- **依赖与边界**：需产品定位决策（§7）。守住"调度无 LLM"护城河，不向自由 GroupChat 靠拢。

### C11 · 真实任务评测证据｜底座｜P0｜≈2–3 人日

- **市面基线**：公开 benchmark / 用户可复现的结果，是"能力对准市面"的证明方式。
- **现状证据**：evals 仅 4 条 mock smoke + 2 条 revision case；R46 自述"要看到差异需要一批产物确实缺验收标准的 case"；
  真实跑仅玩具目标（单次 $0.01–0.16）。R48 已证明"mock 全绿≠真实可用"（复核误判只有真跑才暴露）。
- **目标状态**：有一份可复现、含真实模型的能力报告，且能持续守住能力不回退。
- **落地做法**：从 4 条扩到 20–30 条真实小目标（代码/文档/数据三类，含驳回类 case）；
  夜间限额真实模型 smoke（`--max-cost` 兜底），复用 `eval --variant` / pass^k 出报告。
- **验收标准**：报告含 pass^k / 成本 / 调用数 / 失败归因，进发布门槛；mock 与真实双轨。
- **依赖与边界**：框架已在（P2-5/R46/R47），缺的是**数据**。没有这份报告，
  "能力对准市面"无法被证明，也无法被持续守住。预算需用户定（§7）。

### C12 · 发布与部署证据｜底座｜P0｜≈1–2 人日

- **市面基线**：可一键部署，陌生人按文档能跑起来。
- **现状证据**：CI 四版本矩阵结果待查、Docker 本机未实测、master 领先 2 提交未推送（§0/§7）。
- **目标状态**：一个陌生人按 README 从零部署成功——这是"落地"的定义。
- **落地做法**：推送 2 个提交 → 查 GitHub Actions 四版本矩阵 + studio job + 覆盖率门槛首次结果并回填
  PROJECT-STATE → 目标机 `docker compose build` 实测（验非 root 对 output/ 写权限）→ 打 tag、SDK 发 PyPI（或私有源）。
- **验收标准**：CI 全绿证据入档；陌生人部署成功。
- **依赖与边界**：无前置，立即可做。是"能被别人用上"的最后一公里。

### C13 · SDK 生态｜支柱⑤｜P2｜按需

- **市面基线**：多语言 / 异步客户端。
- **现状证据**：仅 Python 同步零依赖客户端（R16）。
- **目标状态**：非 Python 调用方也能接入。
- **落地做法**：按 openapi.yaml 生成 TS SDK / 异步客户端（契约守卫 R21 已锁死）。
- **依赖与边界**：有真实非 Python 调用方再做。

### C14 · 容量与横向扩展｜底座｜P2｜按需

- **市面基线**：云端多租户、可横向扩展。
- **现状证据**：单进程 asyncio，serve 容量未压测（§7）。
- **目标状态**：真实并发下有可信容量数字与扩展路径。
- **落地做法**：先压测出数字，再决定多进程/队列，不提前分布式。
- **依赖与边界**：serve 出现真实并发瓶颈再做；延续"不引分布式 runtime"红线。

## 4. 市面能力基线（调研摘要）

对 2026-11 公开信息的归纳（来源见 §9；定性判断，非精确数据）：

1. **联网获取信息是标配**：通用 agent 以深度调研为一等场景；浏览器操作成独立产品赛道。
2. **沙箱级代码执行是 Coding agent 底线**：OpenHands 全操作进 Docker；Codex CLI 默认开沙箱、
   Claude Code sandboxed bash；E2B（Firecracker，约 150ms 冷启动）成通用执行后端。
3. **执行→观察→修正闭环**：产出质量靠真实执行兜底，而非评审模型打分。
4. **多模态输入普及**："截图理解→改前端→再截图对比"是主流 UI 工作流。
5. **互操作协议成型**：MCP 双向是事实标准；A2A 由 LF 托管、150+ 组织、v1.0 + 签名 Agent Card，
   但真实落地深度有争议，投入以"最小可用 + 按需扩展"为度。
6. **异步与事件驱动**：事件触发自动化、云电脑是通用 agent 常态，而非只有同步 CLI。

## 6. 明确不做 / 无差距不投入

**无差距，不重复建设**（均已闭环且有测试钉住，出处 PROJECT-STATE）：
确定性 DAG + 条件分支（R4/R31）、动态委派 + 多级主管 + 换人（R6–R10/R33）、
持久化 HITL + 断点 + 超时（R4/R20/R30/P2-7）、崩溃恢复（R17/R22/P2-2）、
原生 FC + 流式工具调用（P2-1/P2-6/R37）、模型韧性（R45）、安全（R25/R35/P2-4/P3-1）、
可观测（P2-3/R50）、evals 框架（P2-5/R46/R47）、可视化编排（R26/R28）、
长上下文压缩、审计脱敏。

**明确不做**（延续既有方案 §5.4 并补充）：
- 不引入分布式 runtime / Temporal Server / K8s / 向量数据库服务；
- 不自研浏览器内核、云电脑、通用消费级对话产品——能力借 MCP/可选依赖，定位保持编排引擎；
- 不用 LangGraph/FastAPI 重写，不向自由 GroupChat 靠拢（确定性调度是护城河）；
- 不以测试数量当质量指标——每项新能力必须带**真实模型端到端证据**，而不是只加单测。

**统一红线**（所有新能力遵守）：默认关闭、四通道登记（YAML/env/export-import/API options）、
离线可测、密钥不落盘、确定性引擎不动、测试只增不减。

## 7. 风险与待决策

1. **Docker 依赖 vs 零依赖红线**：沙箱做成可选后端、默认 local 行为不变（同 R35 先例），
   不破坏离线可测；文档必须写清"生产跑代码请开 docker 后端"。
2. **真实评测成本**：夜间限额 + `--max-cost` 硬上限（已有机制），预算需用户定（原方案 §10 未决问题 3）。
3. **浏览器/搜索扩大注入面**：`untrusted_inputs` 只读预设 + guardrails 规则扩展必须与 C6/C1 同步落地，
   THREAT_MODEL 同步更新（其 §9 维护规则已要求）。
4. **产品定位未决**（原方案 §10 未决问题 2）：本文默认假设为"**通用多智能体编排引擎，
   软件团队是第一个垂直场景**"。若坚守纯软件团队垂直定位，C4/C6 优先级可降，
   但 C1/C2/C3/C11/C12 任何定位下都是阻断项。
